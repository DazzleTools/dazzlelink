# Human Test Checklist: PyPI src/ Layout Migration (Monolith Deprecation, Part 1)

**Target version:** 0.7.0
**Ships with commit:** TBD -- staged as "refactor!: restructure for PyPI -- src/ layout, deprecate monolith"
**Companion automated tests:** 5 tests in `tests/test_version.py` (version format, PEP 440 conversion, component sync)

## What this is

This checklist verifies the staged repository restructure: the package moved from
`dazzlelink/` to `src/dazzlelink/`, the 4,400-line monolith moved from `dazzlelink.py`
to `legacy/dazzlelink_monolith.py`, legacy packaging files (`setup.py`, `setup.cfg`,
`requirements.txt`) were deleted, and `pyproject.toml` became the single source of
packaging truth (py>=3.10, src-layout `packages.find`, pywin32 as a core Windows
dependency, `dazzlelink` console entry point). It also covers the updated Windows
file-association scripts that now prefer the pip-installed module over the monolith.

The restructure claims "no behavior change" -- this checklist exists because layout
migrations are exactly the kind of refactor that silently breaks packaging
(missing subpackages in wheels), version tooling (hooks that look for the old
path), and invocation methods (file associations pointing at a moved monolith).

Anyone with Python 3.10+ and a clone of the repo can run it. A full pass takes
~25-35 minutes; the High-Value section alone takes ~5 minutes.

## Prerequisites

1. Windows 10/11 (primary target) or Linux/macOS (cross-platform sections), Python >= 3.10.
2. A clone of the repo with the restructure applied (staged or committed).
3. `pip install build` available in your main environment (for HV.1).
4. **State isolation -- non-negotiable:**
   - ALL filesystem link/file operations happen inside a fresh sandbox under the temp directory. Never run create/import/convert/mirror/rebase against a real project directory.
   - **DO NOT execute** `scripts/dazzlelink_file_association_in_administrative_shell.bat` or `.ps1` -- they write to the Windows registry. Section 5 inspects their logic without running them.
   - If `~/.dazzlelinkrc.json` exists, back it up first (see Cleanup) -- the `config` test can modify it.

**Create the sandbox** (pick your shell):

**cmd.exe**:
```cmd
set DLTEST=%TEMP%\dazzlelink-checklist
if exist "%DLTEST%" rmdir /s /q "%DLTEST%"
mkdir "%DLTEST%\real" "%DLTEST%\links" "%DLTEST%\out"
echo hello dazzlelink > "%DLTEST%\real\target.txt"
```

**PowerShell**:
```powershell
$env:DLTEST = "$env:TEMP\dazzlelink-checklist"
if (Test-Path $env:DLTEST) { Remove-Item -Recurse -Force $env:DLTEST }
New-Item -ItemType Directory -Force "$env:DLTEST\real", "$env:DLTEST\links", "$env:DLTEST\out" | Out-Null
"hello dazzlelink" | Set-Content "$env:DLTEST\real\target.txt"
```

**POSIX**:
```bash
export DLTEST=/tmp/dazzlelink-checklist
rm -rf "$DLTEST"
mkdir -p "$DLTEST/real" "$DLTEST/links" "$DLTEST/out"
echo "hello dazzlelink" > "$DLTEST/real/target.txt"
```

**Reset between sections**: delete and recreate the sandbox with the same commands.

**Note on symlink creation (Windows)**: creating real symlinks requires either
Developer Mode or an elevated shell. Sections that need a real symlink are
flagged `[needs symlink privilege]`. If you lack it, those steps may fall back
to copies or fail -- note which happened; the fallback message quality is
itself under test.

## High-Value Verification (~5 minutes)

**If you only have 5 minutes**, run these 5 tests.

### HV.1 -- Wheel builds and contains the operations subpackage

Validates: the headline packaging fix -- `[tool.setuptools] packages = ["dazzlelink"]`
previously omitted `dazzlelink.operations`, which would have shipped a broken wheel.

- [ ] **Steps** (cross-shell, from repo root):
  ```
  python -m build --wheel --outdir build-test-dist
  python -c "import zipfile,glob; names=zipfile.ZipFile(glob.glob('build-test-dist/*.whl')[0]).namelist(); print('\n'.join(n for n in names if n.endswith('.py')))"
  ```
- [ ] **Expected:** listing includes `dazzlelink/operations/__init__.py`, `core.py`, `batch.py`, `links.py`, `recreate.py`, `timestamps.py` alongside the top-level modules. No `src/` prefix inside the wheel. No `legacy/` or `scripts/` entries.
- [ ] **Why this matters:** if `operations/` is missing, every installed copy fails at import time -- the single worst packaging failure this restructure was meant to fix.

### HV.2 -- Fresh-venv install: import, entry point, module invocation

Validates: src-layout discovery, console script, `python -m` path.

- [ ] **Steps** (PowerShell shown; analogous in cmd/POSIX -- adjust `Scripts` to `bin` on POSIX):
  ```powershell
  python -m venv "$env:DLTEST\venv"
  & "$env:DLTEST\venv\Scripts\pip" install (Get-Item build-test-dist\*.whl).FullName
  & "$env:DLTEST\venv\Scripts\python" -c "import dazzlelink, dazzlelink.operations; print(dazzlelink.__version__)"
  & "$env:DLTEST\venv\Scripts\dazzlelink" --version
  & "$env:DLTEST\venv\Scripts\python" -m dazzlelink --help
  ```
- [ ] **Expected:** import prints the full version string (e.g., `0.7.0_main_38-...`); `dazzlelink --version` works (console entry point resolved); `--help` lists all 10 subcommands (create, export, import, scan, convert, mirror, execute, config, check, rebase).
- [ ] **Why this matters:** proves the wheel works in an environment that has never seen the repo -- the actual PyPI consumer experience.

### HV.3 -- Core round-trip in the sandbox: create -> execute --mode info

Validates: the primary user workflow under the new layout.

- [ ] **Steps** (cross-shell; quote paths; use the venv's python from HV.2 or the repo checkout):
  ```
  python -m dazzlelink create "<SANDBOX>/real/target.txt" "<SANDBOX>/links/target.txt.dazzlelink"
  python -m dazzlelink execute --mode info "<SANDBOX>/links/target.txt.dazzlelink"
  ```
- [ ] **Expected:** create succeeds and writes a JSON `.dazzlelink` file; execute --mode info prints target info (path, existence) without opening anything. Exit code 0 on both.
- [ ] **Why this matters:** create + execute is what the Windows file association invokes; if this breaks, double-clicking any `.dazzlelink` file breaks.

### HV.4 -- Monolith still works from legacy/

Validates: the migration's "leave the original monolith functional" promise.

- [ ] **Steps** (from repo root, cross-shell):
  ```
  python legacy/dazzlelink_monolith.py --help
  python legacy/dazzlelink_monolith.py create "<SANDBOX>/real/target.txt" "<SANDBOX>/links/mono.dazzlelink"
  python legacy/dazzlelink_monolith.py execute --mode info "<SANDBOX>/links/mono.dazzlelink"
  ```
- [ ] **Expected:** all three succeed. The monolith is self-contained -- moving it must not have broken it.
- [ ] **Why this matters:** the monolith is the working fallback during the deprecation window; the file-association scripts still reference it as last resort.

### HV.5 -- PEP 440 version for pip vs full version for humans

Validates: the version system survives the layout move (`version = {attr = "dazzlelink._version.PIP_VERSION"}` now under `src/`).

- [ ] **Steps** (in the HV.2 venv):
  ```
  pip show dazzlelink
  python -m dazzlelink --version
  ```
- [ ] **Expected:** `pip show` reports clean PEP 440 `0.7.0` (no underscore/branch suffix); `--version` reports the full internal string `0.7.0_main_<build>-<date>-<hash>`.
- [ ] **Why this matters:** a non-PEP-440 version makes the dist unpublishable to PyPI; a broken attr path makes the build fail entirely.

## Section 1: Packaging deep checks (~5 min)

### 1.1 sdist content audit

- [ ] **Steps** (cross-shell, repo root):
  ```
  python -m build --sdist --outdir build-test-dist
  python -c "import tarfile,glob; print('\n'.join(tarfile.open(glob.glob('build-test-dist/*.tar.gz')[0]).getnames()))"
  ```
- [ ] **Expected:**
  - Contains `src/dazzlelink/**` (all 13 .py files), `tests/`, `docs/`, `examples/`, `README.md`, `LICENSE`, `pyproject.toml`, `MANIFEST.in`.
  - Does NOT contain: `legacy/` (monolith not shipped), `scripts/.github/`, `scripts/tests/`, `scripts/docs/`, `scripts/.repokit.json`, `scripts/pyproject.toml.*`, `private/`, any `__pycache__` or `.pyc`.
- [ ] **Check:** note whether ANY `scripts/` files are present. `recursive-include scripts *` was removed -- decide deliberately whether the file-association scripts SHOULD ship in the sdist (currently they don't; flag as a design question, not a bug).

### 1.2 Deleted packaging files are really gone (and nothing references them)

- [ ] **Steps**:

  **cmd.exe**:
  ```cmd
  dir setup.py setup.cfg requirements.txt 2>nul
  findstr /s /m "setup.py setup.cfg requirements.txt" .github\workflows\*.yml README.md CONTRIBUTING.md docs\*.md
  ```

  **PowerShell**:
  ```powershell
  Test-Path setup.py; Test-Path setup.cfg; Test-Path requirements.txt
  Select-String -List -Pattern "setup\.py|setup\.cfg|requirements\.txt" -Path .github\workflows\*.yml, README.md, CONTRIBUTING.md, docs\*.md
  ```

  **POSIX**:
  ```bash
  ls setup.py setup.cfg requirements.txt 2>/dev/null
  grep -rlE "setup\.py|setup\.cfg|requirements\.txt" .github/workflows/ README.md CONTRIBUTING.md docs/ 2>/dev/null
  ```
- [ ] **Expected:** the three files do not exist. Any doc/CI references found are stale and must be fixed before commit (CI invoking `pip install -r requirements.txt` would now fail).

### 1.3 Stale root egg-info from the old layout

- [ ] **Steps** (cross-shell):
  ```
  python -c "print(open('dazzlelink.egg-info/SOURCES.txt').read())"
  ```
- [ ] **Expected:** this egg-info predates the move (references old `dazzlelink/` paths). It is build debris, not source.
- [ ] **Check:** confirm `dazzlelink.egg-info/` is gitignored or untracked; it should be deleted before the commit (use `dz safedel` if available) and regenerated under `src/` by the next editable install. Verify a fresh `pip install -e .` creates `src/dazzlelink.egg-info/` and the root one stays gone.

### 1.4 pywin32 dependency lands on Windows (and not elsewhere)

- [ ] **Steps** (in the HV.2 venv, Windows):
  ```
  pip show pywin32
  ```
- [ ] **Expected:** pywin32 installed automatically (now a core dep via `sys_platform == 'win32'` marker, not an extra). On POSIX, `pip show pywin32` should find nothing.

## Section 2: Full command sweep -- module (`python -m dazzlelink`) (~10 min)

Run everything against the sandbox. Reset the sandbox first.

### 2.1 create / execute (already covered in HV.3 -- re-verify JSON shape)

- [ ] **Steps** (cross-shell):
  ```
  python -m dazzlelink create "<SANDBOX>/real/target.txt" "<SANDBOX>/links/t1.dazzlelink"
  python -m json.tool "<SANDBOX>/links/t1.dazzlelink"
  ```
- [ ] **Expected:** valid JSON with `target_path`, `target_representations` (including `relative_path` -- the v0.7.0 feature), `config.default_mode`, timestamps. Note output readability: is the created-file message clear about what was written where?

### 2.2 export / import round-trip `[needs symlink privilege]`

- [ ] **Steps** (PowerShell, elevated or Developer Mode):
  ```powershell
  New-Item -ItemType SymbolicLink -Path "$env:DLTEST\links\real-link.txt" -Target "$env:DLTEST\real\target.txt" | Out-Null
  python -m dazzlelink export "$env:DLTEST\links\real-link.txt" "$env:DLTEST\out\real-link.dazzlelink"
  Remove-Item "$env:DLTEST\links\real-link.txt"
  python -m dazzlelink import "$env:DLTEST\out\real-link.dazzlelink" --target-dir "$env:DLTEST\links"
  Get-Item "$env:DLTEST\links\real-link.txt" | Select-Object LinkType, Target
  ```

  **POSIX**:
  ```bash
  ln -s "$DLTEST/real/target.txt" "$DLTEST/links/real-link.txt"
  python -m dazzlelink export "$DLTEST/links/real-link.txt" "$DLTEST/out/real-link.dazzlelink"
  rm "$DLTEST/links/real-link.txt"
  python -m dazzlelink import "$DLTEST/out/real-link.dazzlelink" --target-dir "$DLTEST/links"
  ls -la "$DLTEST/links/"
  ```
- [ ] **Expected:** export serializes the symlink; import recreates it pointing at the same target. If unprivileged on Windows, expect a clear error message (not a stack trace) -- judge the message quality.

### 2.3 scan / check

- [ ] **Steps** (cross-shell):
  ```
  python -m dazzlelink scan "<SANDBOX>"
  python -m dazzlelink check "<SANDBOX>"
  ```
  (Recursive is the default; pass `--no-recursive` to limit depth.)
- [ ] **Expected:** scan reports any symlinks under the sandbox; check reports broken ones (create one by deleting `real/target.txt` after making a link to it, then restore). Output should be readable -- columns/paths not garbled on cmd.exe codepage 437.

### 2.4 convert `[needs symlink privilege]`

- [ ] **Steps**: with at least one real symlink in `<SANDBOX>/links` (convert writes `.dazzlelink` files in place next to each symlink; there is no `--output-dir`):
  ```
  python -m dazzlelink convert "<SANDBOX>/links"
  ```
- [ ] **Expected:** each symlink produces a `.dazzlelink` file in the output dir. **KNOWN RISK**: if the code path passes `make_executable=True` (config default or flag), this raises `AttributeError: 'DazzleLink' object has no attribute '_make_dazzlelink_executable'` (`core.py:313`, issue #18 -- fix deferred). Record exactly which invocations trigger it; default invocations should NOT.

### 2.5 mirror `[needs symlink privilege]`

- [ ] **Steps**:
  ```
  python -m dazzlelink mirror "<SANDBOX>/links" "<SANDBOX>/out/mirror"
  ```
- [ ] **Expected:** recreates the link structure under the destination. Same #18 caveat as 2.4.

### 2.6 rebase (symlink rebase only -- dazzlelink-file rebase is monolith-only, #15)

- [ ] **Steps** (no `--dry-run` flag exists -- run against a disposable copy of the links dir; flag the missing dry-run as a UX follow-up):
  ```
  python -m dazzlelink rebase "<SANDBOX>/links" --relative
  ```
- [ ] **Expected:** lists conversions performed (or none if no symlinks). Verify the rest of the sandbox is untouched (re-run `scan`). Note: `rebase --only-broken` without path flags does symlink rebase here, NOT `.dazzlelink` JSON rebase as in the monolith -- a documented gap (#15/#18), not a regression of this restructure.

### 2.7 config (isolated)

- [ ] **Steps**: check whether config supports a path override; if it only writes `~/.dazzlelinkrc.json`, ONLY run the read path:
  ```
  python -m dazzlelink config --view
  ```
- [ ] **Expected:** prints current config (defaults if no rc file). Do not run `config --set` unless your real rc file is backed up.

## Section 3: Monolith parity spot-checks (~5 min)

Reset sandbox. Repeat 2.1, 2.3, 2.6 with `python legacy/dazzlelink_monolith.py ...` instead of `python -m dazzlelink ...`.

- [ ] **3.1** create + execute --mode info parity: same files produced; note the monolith's RICHER info display (relative path, creation date, live size) vs the package's basic one -- known gap #18, document, don't fail.
- [ ] **3.2** scan parity: same links found.
- [ ] **3.3** `python legacy/dazzlelink_monolith.py rebase --only-broken "<SANDBOX>"`: the monolith routes this to `.dazzlelink` JSON rebase -- confirm it still works from the new path.
- [ ] **3.4** Confirm no import shadowing: from the repo root, `python -c "import dazzlelink; print(dazzlelink.__file__)"` must resolve to the installed/src package, never to the monolith (the old root `dazzlelink.py` shadow risk is gone -- that's a key win of this move).

## Section 4: Version tooling and hooks (~3 min)

### 4.1 sync-versions.py --auto handles the src layout

- [ ] **Steps** (cross-shell, repo root -- read-only first):
  ```
  python scripts/sync-versions.py --check
  ```
- [ ] **Expected:** finds `src/dazzlelink/_version.py` via `[tool.repokit-common] version-source` in pyproject.toml; reports versions in sync (or explains drift). Must NOT error with "could not find _version.py".

### 4.2 Pre-commit hook dry run

- [ ] **Steps** (POSIX/git-bash):
  ```bash
  bash .git/hooks/pre-commit
  git status --short
  ```
- [ ] **Expected:** hook completes; if it modified `src/dazzlelink/_version.py` (build metadata bump), that's its normal behavior -- verify it edited the SRC copy, not a phantom old path. **Known limitation:** `bash scripts/update-version.sh` (the deprecated fallback) fails on src-layout until the repokit-common subtree is updated to >= v0.2.5 -- expected, deferred to the scripts/ reorganization commit.

## Section 5: File-association scripts -- INSPECTION ONLY (~3 min)

**DO NOT RUN THESE SCRIPTS.** They write `HKCR` registry entries. Verify logic by reading and by simulating their detection steps.

- [ ] **5.1 Detection order**: read both `scripts/dazzlelink_file_association_in_administrative_shell.bat` and `.ps1`. Confirm priority is now: (1) `python -c "import dazzlelink"` succeeds -> use `python -m dazzlelink`; (2) `where dazzlelink` -> module invocation; (3) legacy monolith fallback -- and the monolith fallback path checks `..\dazzlelink.py` relative to `scripts/`, which NO LONGER EXISTS after the move. Confirm the script's "not found" error handling is reachable and its message is accurate (it should arguably check `..\legacy\dazzlelink_monolith.py` -- flag as follow-up if not).
- [ ] **5.2 Simulate detection step 1** (harmless, no registry):
  ```
  python -c "import dazzlelink" && echo MODULE-FOUND
  ```
  (cmd: `python -c "import dazzlelink" && echo MODULE-FOUND`; PowerShell: `python -c "import dazzlelink"; if ($LASTEXITCODE -eq 0) { "MODULE-FOUND" }`)
- [ ] **Expected:** MODULE-FOUND when the package is installed -- i.e., real machines that ran `pip install -e .` will take the module path, never the monolith.
- [ ] **5.3 No Unicode hazards**: confirm neither script contains em dashes, smart quotes, arrows, or checkmark characters (codepage 437/1252 parse hazards).

## What the automated tests DON'T cover

- Wheel/sdist contents and fresh-venv installability (Sections HV.1, HV.2, 1.1)
- Real symlink creation/round-trips with Windows privilege quirks (2.2, 2.4, 2.5)
- Shell rendering on cmd.exe codepage 437 vs PowerShell 1252 (2.3, 5.3)
- Registry-adjacent file-association logic (Section 5)
- Git hook behavior against the real working tree (Section 4)
- Error message quality for unprivileged/missing-target cases
- The monolith's continued operability from `legacy/` (Section 3)
- Import shadowing resolution (3.4)

## Reporting issues found

1. Note the section and step number, your shell, and elevation state.
2. Capture the exact command and full output (`> "%TEMP%\dl-fail.txt" 2>&1`).
3. Distinguish: regression of THIS restructure vs pre-existing gap (#18/#19/#15 are known).
4. File a GitHub issue referencing this checklist filename and the staged commit.
