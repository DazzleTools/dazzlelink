## Detailed Evidence

### HV.2 FAIL -- Generated Script SyntaxError (Critical)

**Test command:**
```powershell
python "$env:TEMP\dl-c1\link.txt.dazzlelink" --info
```

**Actual output:**
```
  File "C:\Users\Extreme\AppData\Local\Temp\dl-c1\link.txt.dazzlelink", line 2
    """:"
    ^^^^^
SyntaxError: (unicode error) 'unicodeescape' codec can't decode bytes in position 228-229: truncated \UXXXXXXXX escape
```

**Root cause:** The polyglot header in `make_dazzlelink_executable` (links.py lines 435-462) uses a triple-quoted string `""":"..."""` to embed the batch script section. The target path is written verbatim into this string using plain `f.write()`. When the path contains `\U` (as in `C:\Users\...`) or `\\?\` (UNC extended prefix from symlink resolution), Python's string literal parser treats `\U` as a Unicode escape sequence `\UXXXXXXXX` -- which requires exactly 8 hex digits. The path value `\Users` provides only 5 characters, triggering the SyntaxError.

**Reproducing without UNC path:** Even with a simple path like `C:\Users\Extreme\AppData\Local\Temp\dl-c1\target.txt`, the `\U` in `\Users` causes the same SyntaxError (confirmed separately).

**Scope:** This affects ALL Windows users whose TEMP or target paths pass through `C:\Users\`. This is essentially every standard Windows installation. The generated script is non-functional on all such systems.

**Generated script structure (first 22 lines):**
```
1:  #!/bin/sh
2:  """:"
3:  :: Windows Batch Script
4:  @echo off
5:  if "%~1"=="" goto show_info
...
12: :open_target
13: start "" "C:\Users\Extreme\AppData\Local\Temp\dl-c1\target.txt"
14: exit /b
...
18: echo Target: C:\Users\Extreme\AppData\Local\Temp\dl-c1\target.txt
...
22: """
```

The `start ""` and `echo Target:` lines (13, 18) embed the raw Windows path with backslashes inside the triple-quoted Python string block. Python cannot parse this as a string literal when `\U` appears.

**Fix required (for future commit, not applied here):** In `make_dazzlelink_executable` (links.py, lines ~453, ~458), paths written into the batch section of the triple-quoted block must have their backslashes doubled, or the block must use a raw string approach, or the batch section must be terminated before those path literals appear.

Minimal fix example:
```python
# In the batch section writes:
escaped_target = target_path.replace('\\', '\\\\')
f.write(f'start "" "{escaped_target}"\n')   # was: f'start "" "{target_path}"\n'
f.write(f'echo Target: {escaped_target}\n')  # was: f'echo Target: {target_path}\n'
```

### Secondary Finding: Duplicate DAZZLELINK_DATA_BEGIN Marker

The generated script's `main()` function (inside the Python portion) contains the comparison string `"# DAZZLELINK_DATA_BEGIN"` as a Python string literal (the loop that parses the embedded JSON). The actual data section marker `# DAZZLELINK_DATA_BEGIN` appears later. When searching the file linearly, the code finds the string-literal occurrence first (at byte position ~862) before reaching the actual data section marker (at byte position ~5076). This means the generated script's JSON-parsing loop would read code body content as JSON and fail with a JSONDecodeError even after the `\U` SyntaxError is fixed.

**Fix required:** The `main()` function inside the generated script needs to look for the second occurrence of the marker, or use a more distinctive marker like `## DAZZLELINK_DATA_BEGIN ##` that does not appear in the Python source comparison string.

### 2.2 UX Note -- Exit Code 0 on Execute Failure

When a target file is missing during `execute`, the error is well-structured:
```
ERROR: Failed to execute dazzlelink ...: Target not found. Tried:
  Absolute: C:\Users\Extreme\AppData\Local\Temp\dl-c1\target.txt
  Relative: target.txt
  Representations: ['original_path', 'relative_path']
```

However, **the process exits with code 0** even on this failure path. The error message is readable and helpful, but the exit code is incorrect for scripting use. Callers cannot detect failure via `$LASTEXITCODE`. This is a UX/reliability concern.

**Expected:** exit code 1 (or non-zero) when target resolution fails.

### Section 1.1 Note -- JSON Section Parses with Correct default_mode

Although the generated executable script itself fails to run (HV.2 FAIL), the embedded JSON payload at the second `# DAZZLELINK_DATA_BEGIN` marker is structurally correct: `"default_mode": "open"` appears at line 207 of the generated file, confirming that `--mode open` was forwarded through the convert/config chain.

## UX Observations

1. **Exit code 0 on failure (2.2):** The `execute` command returns exit code 0 even when the target is not found. Should return non-zero.
2. **Generated script unusable on standard Windows (HV.2):** The polyglot script pattern breaks on any path containing `\U`, `\A`, `\N`, `\T`, or other Python escape characters. This is every standard Windows user profile path (`C:\Users\...`).
3. **Duplicate marker problem in generated script:** The `DAZZLELINK_DATA_BEGIN` marker appears both as a string comparison value in the Python `main()` code and as the actual data separator. A linear search would find the wrong one first.
4. **update-config not yet a CLI subcommand:** This is expected per the checklist ("scheduled for the next parity commits"). The import smoke confirms no NameError.
5. **PowerShell New-Item -ItemType SymbolicLink fails despite Developer Mode registry key=1:** Python `os.symlink` works fine. The registry flag is active but PowerShell's cmdlet path requires a separate privilege check. This is a system-level quirk, not a dazzlelink issue.

## SHIP / HOLD Verdict

**Verdict: HOLD**

The parity Commit 1 fixes are confirmed working at the module level -- the AttributeError (#18) is gone, both `import json` fixes (links.py and batch.py) are in place, the execute mode precedence (#19) is correctly ordered (CLI > file-embedded > global > "info"), and all 10 automated tests pass. The flag-forwarding chain (--executable, --mode) through convert/mirror/execute is wired correctly.

However, HV.2 reveals a **blocking regression in the generated executable script**: any path containing `\U` (i.e., any standard `C:\Users\...` path) causes a Python SyntaxError at parse time, making the generated script completely non-functional on essentially every Windows system. This is the headline user-facing feature of the `--executable` flag -- a script that cannot be run is worse than no script at all. Additionally, a secondary bug means that even after the `\U` escape is fixed, the JSON-parsing loop inside the generated script would find the wrong `DAZZLELINK_DATA_BEGIN` marker occurrence.

The automated tests do not catch HV.2 because they mock the generation path without actually executing the generated file under a real interpreter. This is precisely the gap the checklist was designed to expose.

The HOLD is specifically for the `--executable` / `make_dazzlelink_executable` functionality. The mode-precedence fix (#19) and the import fixes (#18) are solid and could ship independently if the executable generation were gated or removed. Recommend filing a bug against `links.py:make_dazzlelink_executable` before merging this commit.
