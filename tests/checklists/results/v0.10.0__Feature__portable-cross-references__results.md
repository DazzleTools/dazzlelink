### Bug: `get_locators()` crashes on unhashable `target_representations` values

**Severity:** REVIEW (not blocking for this release; a hardening gap, not a regression)

**Repro:**
```python
from dazzle_linklib import DazzleLinkData
rec = DazzleLinkData()
rec.to_dict().setdefault("link", {})["target_representations"] = {
    "subst_path": ["not", "a", "string"],   # or any dict value
}
rec.get_locators()
# TypeError: unhashable type: 'list'
```

**Location:** `dazzle_linklib/record.py`, `get_locators()`, around the line `pair = (kind, value); if pair not in seen:` -- when `value` is a list/dict, the tuple itself becomes unhashable and the `in` membership test raises.

**CLI-level impact confirmed:** a hand-corrupted `.dazzlelink` record (a plausible external-edit / corruption scenario, JSON has no type constraint) with a list value in `target_representations`:
- `dazzlelink execute --mode info` -- **unaffected** (doesn't call `get_locators()`).
- `dazzlelink execute --mode open` -- crashes, but is caught by the tool's exception wrapper, producing a clean one-line error rather than a raw traceback: `ERROR: Failed to execute dazzlelink ...: unhashable type: 'list'`. The message gives no indication of which field or record caused it.

**Why not blocking:** every internal writer (`path_family`, `populate_locators`) always calls `str(value)` before storing, so this cannot occur through any normal create/populate path in 0.10.0 -- it requires a hand-edited or corrupted on-disk JSON file. Recommend a follow-up hardening issue (coerce to `str()` or skip non-string values defensively in `get_locators()`, with a clearer error message) rather than holding this release for it.

## Incident: stray `Q: => D:\` subst alias, and a leaked file on the real network share

During the HV.4 re-verification (a bash script simulating subst alias death), a `subst Q: <scratch-dir>` remap command failed with `Drive already SUBSTed` -- at that moment `Q:` was already mapped to `D:\` (the box's real `net use` mapped drive, `D:\` <-> `\\aktuldjr\d`), even though the prior Part C.1 subst test had cleanly freed `Q:` at its own completion (confirmed by that script's own successful `subst Q: /d` cleanup, rc=0). No command in between touched `subst` at all, so the reappearance of `Q: -> D:\` is unexplained from this session's own actions -- possibly an external process or scheduled script on this machine re-establishes that mapping, or it predates this session in a way the initial `Get-PSDrive -PSProvider FileSystem` survey didn't surface (that survey is not a fully reliable way to detect subst drives).

Because the remap silently failed, the subsequent `dazzlelink create Q:\hv4.txt Q:\hv4.txt.dazzlelink` command wrote its **output** through the stale `Q: -> D:\` mapping, creating a real file at `D:\hv4.txt.dazzlelink` (== `\\aktuldjr\d\hv4.txt.dazzlelink`) on the user's real network share -- outside the authorized scratch zone. This was caught immediately by the next step in the same script (a follow-up `execute --mode info` failed with "No such file or directory" for the expected *local* path), which prompted an investigation that confirmed the leaked file.

**Remediation taken:**
- The leaked file was removed via `dz safedel --yes "D:\hv4.txt.dazzlelink"` (recoverable in the safedel trash store for ~30 days; staged `2026-07-30__10-47-55`).
- The `Q: -> D:\` alias itself was deliberately left untouched at the time, since its provenance was unknown and further guessing risked making things worse. All further `subst`-based testing was halted for the rest of the run (no more `subst` commands were issued in this session past this point); Part C.1's earlier clean run already covered HV.4's mechanism.
- The coordinator has since removed the stray `Q:` alias from the system.

**Where this happened, precisely:** the failure point was the second `subst` command in the HV.4 re-verification script (`subst Q: "$(cygpath -w "$SCRATCH" ...)"`), immediately followed by the `dazzlelink create Q:\hv4.txt Q:\hv4.txt.dazzlelink` call that actually performed the leaked write. No hang occurred in the test execution itself -- the interruption the coordinator referenced (session paused ~9h) happened later, after cleanup was already complete and while this report was being written, and appears to be a session/infra pause rather than something caused by the test run.

## Verdict: **SHIP**

**Rationale:** All three regression suites are green with exactly the expected counts (unctools 62/2/2, linklib 89, dazzlelink 58). All 9 Rnd4 acceptance checks (AC-A through AC-I) pass, including the real end-to-end moved-tree scenario (AC-I) and the polyglot-executable scenario (AC-G) via the real CLI. Cross-machine live re-resolution was independently confirmed against this box's actual `net use` mapping. Hostile probing (wrong-file heuristic, empty/garbage input, unicode, long paths, unknown keys) surfaced only one narrow finding -- a crash on hand-corrupted non-string JSON values, which cannot arise from any of the library's own write paths and does not regress any shipped guarantee -- appropriate for a follow-up hardening issue, not a release blocker. The only operational issue (the stray subst alias / leaked network-share file) was a testing-environment incident, fully remediated, and unrelated to the shipped code's correctness.

**Recommended follow-ups (non-blocking):**
- File a hardening issue for `get_locators()` to tolerate non-string `target_representations` values gracefully (coerce or skip with a clear message) rather than raising a raw `TypeError`.
- AC-E was validated via the existing automated test rather than a freshly-written empirical script in this run; if a from-scratch confirmation is wanted, `test_populate_then_rebase_single_relative_locator` in `dazzle-linklib/tests/test_locators_population.py` is the reference to re-run in isolation.
