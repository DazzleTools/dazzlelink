# Human Test Checklist: dazzlelink 0.9.0 -- consume the dazzle-linklib library

**Target version:** 0.9.0
**Ships with commit:** the 0.9.0 thinning series (data re-export, recreate /
find_dazzlelinks / rebase_dazzlelinks delegation)
**Companion automated tests:** 40 tool tests (`tests/test_cli_commands.py`,
`tests/test_executable_and_mode_precedence.py`,
`tests/test_rebase_dazzlelinks_and_info.py`, `tests/test_version.py`) +
68 library tests in `dazzle-linklib`.

## What this is

0.9.0 turns dazzlelink into a **thin consumer** of the DazzleLib stack: the link
record (`DazzleLinkData`), record recreation (`recreate_link`), record discovery
(`find_dazzlelinks`), and record-file rebase (`rebase_dazzlelinks`) now live in
the **dazzle-linklib** library (L2) and are called from the tool rather than
implemented in it (~560 source lines removed). This is a refactor that touches
file I/O, symlink creation, timestamp/attribute application, and the record
schema -- exactly the surface where a "pure refactor" can silently drift. This
checklist verifies the tool still behaves identically end-to-end, especially the
anti-link-rot create -> delete -> recreate cycle that mocks don't fully cover.

## Prerequisites

1. **OS**: Windows is the primary target (symlink + timestamp behavior is most
   meaningful there). Symlink creation needs Developer Mode or an elevated shell.
2. **Python**: 3.9+.
3. **Install both packages so the tool consumes the library:**

   **cmd.exe**:
   ```cmd
   pip install -e C:\code\dazzle-linklib --no-deps
   pip install -e C:\code\dazzlelink --no-deps
   ```

   **PowerShell**:
   ```powershell
   pip install -e C:\code\dazzle-linklib --no-deps
   pip install -e C:\code\dazzlelink --no-deps
   ```

   **POSIX**:
   ```bash
   pip install -e /c/code/dazzle-linklib --no-deps
   pip install -e /c/code/dazzlelink --no-deps
   ```
   (Also ensure `dazzle-lib` and `dazzle-filekit>=0.3.0` are installed -- the
   library depends on them.)
4. **State isolation**: every step writes only to a throwaway temp directory you
   create. Nothing touches real data.

### Reset between sections

Delete and recreate the scratch dir. Prefer `dz safedel` if available; else:
  **cmd.exe**: `rmdir /s /q %TEMP%\dzwf & mkdir %TEMP%\dzwf`
  **PowerShell**: `Remove-Item -Recurse -Force $env:TEMP\dzwf; New-Item -ItemType Directory $env:TEMP\dzwf`
  **POSIX**: `rm -rf /tmp/dzwf && mkdir /tmp/dzwf`

## High-Value Verification (~5 minutes)

### HV.1 -- Both test suites are green

Validates: nothing regressed in the tool or the library.

- [ ] **Steps:** `cd C:\code\dazzlelink && python -m pytest -q --no-cov` then
  `cd C:\code\dazzle-linklib && python -m pytest -q`
- [ ] **Expected:** 40 passed (tool) and 68 passed (library).
- [ ] **Why this matters:** the regression floor for the whole thinning.

### HV.2 -- The tool consumes the library, not its own copy

Validates: `DazzleLinkData` is the library's class, not a tool-local duplicate.

- [ ] **Steps:**
  ```
  python -c "from dazzlelink.data import DazzleLinkData as T; import dazzle_linklib as L; print(T is L.DazzleLinkData)"
  ```
- [ ] **Expected:** `True`.
- [ ] **Why this matters:** if it prints `False`, the record model has drifted
  back into two homes -- the whole point of 0.9.0 is one home.

### HV.3 -- The workflow.png demo, end-to-end (the keystone)

Validates: the anti-link-rot create -> dazzle -> delete -> recreate cycle.

- [ ] **Steps** (POSIX shown; adapt paths for your shell):
  ```bash
  cd /tmp/dzwf
  python -c "open('asset.png','w').write('x')"
  python -c "import os; os.symlink('asset.png','asset.lnk.png')"
  dazzlelink create --mode open --config-level file asset.lnk.png asset.lnk.png.dazzlelink
  dazzlelink execute --mode info asset.lnk.png.dazzlelink
  rm asset.lnk.png
  dazzlelink import --use-live-target --pattern "*.dazzlelink" --timestamp-strategy target .
  python -c "import os; print('restored:', os.path.islink('asset.lnk.png'))"
  ```
- [ ] **Expected:** `create` reports success; `info` prints the target/original
  paths; `import` reports "1 links successfully created, 0 errors"; the final
  line prints `restored: True`.
- [ ] **Why this matters:** this is the tool's headline capability; it exercises
  the library's record model + the tool's symlink/timestamp ops together.

### HV.4 -- `recreate` of a single dazzlelink

Validates: the thinned `recreate_link` path (delegates to the library).

- [ ] **Steps:** after HV.3, delete the link again and recreate via the
  `recreate`/`import` command of your choice; confirm the symlink returns.
- [ ] **Why this matters:** `recreate_link` is the most-thinned operation; its
  timestamps + attributes now come through filekit.

### HV.5 -- `--version` reports 0.9.0

- [ ] **Steps:** `dazzlelink --version`
- [ ] **Expected:** `dazzlelink 0.9.0 (...)`.

## Section 2: Discovery + rebase (~4 min)

### 2.1 `rebase` syncs stored paths and prints a summary

- [ ] **Steps:** in a scratch dir, create a real target + a `.dazzlelink` whose
  stored relative path is stale, then `dazzlelink rebase .`.
- [ ] **Expected:** the printed summary shows `1 changed` and a `Changed:`
  block; the new summary line also includes a `skipped` count (new in 0.9.0).
- [ ] **Check:** the `.dazzlelink` file's `relative_path` is recomputed.

### 2.2 `rebase` skips an executable (polyglot) dazzlelink

- [ ] **Steps:** create an executable `.dazzlelink` (`create --executable`),
  place it in a dir with a stale path, run `dazzlelink rebase .`.
- [ ] **Expected:** the summary reports it under `Skipped:` (not `Errors:`), and
  the executable file is left byte-for-byte intact (script wrapper preserved).
- [ ] **Why this matters:** 0.8.0 reported these as cryptic JSON errors; 0.9.0
  reports them clearly and never strips the wrapper. This is a behavior
  improvement to confirm, not just preserve.

### 2.3 Both-broken record reports an error

- [ ] **Steps:** a `.dazzlelink` whose absolute and relative targets both don't
  exist; `dazzlelink rebase .`.
- [ ] **Expected:** reported under `Errors:` (matches 0.8.0).

## What the automated tests DON'T cover

- **Real symlink/junction recreation under elevation** -- the timestamp/attribute
  application through filekit on actual NTFS reparse points.
- **The full `import` CLI against many real files** with mixed formats.
- **Executable `.dazzlelink` files double-clicked** via the Windows file
  association (the fork-bomb-safe execute path).
- **Cross-machine rebase** -- moving a `.dazzlelink` to a machine where only the
  relative path resolves.
- **Performance feel** of discovery/rebase over a large tree.
- **filekit version skew** -- behavior if an older `dazzle-filekit` (<0.3.0) is
  installed (the dependency pin should prevent this, but worth a human check).

## Reporting issues found

1. Note the section/step number, exact command, and full output.
2. Save the offending `.dazzlelink` (sanitize private paths).
3. File against `DazzleTools/dazzlelink`, referencing this checklist and the
   0.9.0 thinning commits.
