**Target version:** 0.7.5 (version TBD at commit)
**Ships with commit:** TBD -- "feat: rebase .dazzlelink files (#15) + richer execute --mode info"
**Companion automated tests:** 6 in `tests/test_rebase_dazzlelinks_and_info.py` (3 rebase cases + in-sync + empty + info display); full suite 37

## What this is

Two parity features the monolith had and the modular package lacked:
- **`rebase` now also fixes `.dazzlelink` files** (GT-4 / #15). Previously `rebase` only rewrote live OS
  symlinks; now it ALSO synchronizes the absolute and relative target paths stored *inside* each
  `.dazzlelink` JSON file (run as a second pass, like the monolith). This is **file-mutating** -- it
  rewrites `.dazzlelink` files on disk.
- **`execute --mode info`** now shows the richer display (GT-8): the portable relative path, and a
  LIVE on-disk `Exists`/`Size`/`Type` check (falling back to the metadata stored at creation when the
  target is gone), instead of only the stored snapshot.

Because `rebase` mutates files, the parts that matter -- the 3-case path logic, file integrity after a
rewrite, recursive scanning, idempotency -- are exactly what only real runs (not mocks) confirm.

## Prerequisites

1. Python >= 3.10, editable install (`pip install -e .`).
2. **State isolation -- important, this mutates files:** ALL `.dazzlelink` files used here are
   throwaway copies in a `%TEMP%`/`/tmp` sandbox. NEVER run `rebase` against a directory holding real
   `.dazzlelink` files you care about.
3. No symlink privilege needed for the `.dazzlelink`-rebase path (they are plain JSON). `rebase` will
   also try to rebase live symlinks in the same directory -- keep the sandbox free of real symlinks, or
   expect that pass to report 0.

**Sandbox (PowerShell):**
```powershell
$env:DLT = "$env:TEMP\dl-2b"
Remove-Item -Recurse -Force $env:DLT -ErrorAction SilentlyContinue
New-Item -ItemType Directory -Force "$env:DLT\d1\sub", "$env:DLT\d2" | Out-Null
"payload-content" | Set-Content "$env:DLT\target.txt"
cd C:\code\dazzlelink
```

**POSIX:**
```bash
export DLT=/tmp/dl-2b
rm -rf "$DLT"; mkdir -p "$DLT/d1/sub" "$DLT/d2"
echo payload-content > "$DLT/target.txt"
cd /path/to/dazzlelink
```

## High-Value Verification (~5 min)

### HV.1 -- rebase recomputes a stale relative path (the headline)

- [ ] **Steps:**
  ```
  python -m dazzlelink create "<DLT>/target.txt" "<DLT>/d1/sub/a.dazzlelink"
  ```
  Note the stored `relative_path` (it's relative to `d1/sub`). Move the file to `d2` (depth changes, so
  the stored relative becomes wrong):

  **PowerShell:** `Move-Item "$env:DLT\d1\sub\a.dazzlelink" "$env:DLT\d2\a.dazzlelink"`
  **POSIX:** `mv "$DLT/d1/sub/a.dazzlelink" "$DLT/d2/a.dazzlelink"`

  Then rebase:
  ```
  python -m dazzlelink rebase "<DLT>/d2"
  ```
- [ ] **Expected:** prints "Rebasing 1 dazzlelink file(s)..." and "Results: 1 changed, ...". The stored
  `relative_path` inside `d2/a.dazzlelink` is recomputed (e.g. `..\..\target.txt` -> `..\target.txt`) and
  now resolves to the real target from `d2`.
- [ ] **Why:** this is the whole point of #15 -- moving a `.dazzlelink` and fixing its stored paths.

### HV.2 -- File integrity after the rewrite

- [ ] **Steps:** after HV.1, confirm `d2/a.dazzlelink` is still valid JSON and only the path changed:
  ```
  python -m json.tool "<DLT>/d2/a.dazzlelink"
  ```
- [ ] **Expected:** valid JSON; `link.target_path` still the absolute target; `link.target_representations.relative_path` is the new value; the rest of the structure intact (no truncation/corruption).
- [ ] **Why:** a rewrite that corrupts the file would be a data-loss bug.

### HV.3 -- Idempotency: a second rebase changes nothing

- [ ] **Steps:** run `python -m dazzlelink rebase "<DLT>/d2"` again.
- [ ] **Expected:** "Results: 0 changed, 1 unchanged, 0 errors". Re-running must be a no-op once in sync.
- [ ] **Why:** non-idempotent rewrites churn files and timestamps endlessly.

### HV.4 -- richer execute --mode info

- [ ] **Steps:**
  ```
  python -m dazzlelink execute --mode info "<DLT>/d2/a.dazzlelink"
  ```
- [ ] **Expected:** output now includes a `Relative Path:` line, and under `Target Details:` shows
  `Exists: Yes`, a `Size:` (live, e.g. bytes/KB), and a `Type:` derived from the extension. Compare to
  the monolith: `python legacy/dazzlelink_monolith.py execute --mode info "<DLT>/d2/a.dazzlelink"`.
- [ ] **Why:** GT-8 -- the package previously showed only stale stored metadata.

## Section 1: rebase 3-case path logic (~5 min)

### 1.1 Absolute broken, relative valid -> recompute absolute
- [ ] Hand-edit a copy's `link.target_path` to a non-existent absolute path while leaving a correct
  `relative_path`, then `rebase`. Expected: "1 changed"; `target_path` recomputed to the resolved
  absolute (now exists).

### 1.2 Both broken -> error, file untouched
- [ ] Hand-edit a copy so BOTH the absolute and relative point nowhere, then `rebase`. Expected: "1
  errors"; the file is reported under Errors and NOT modified.

### 1.3 In sync -> unchanged
- [ ] A freshly created, unmoved `.dazzlelink` then `rebase` in place. Expected: "0 changed, 1 unchanged".

### 1.4 Recursive vs non-recursive
- [ ] Put `.dazzlelink` files at the top level and in a subdir. Default `rebase <dir>` is recursive;
  `--no-recursive` should only touch the top level.

## Section 2: rebase runs BOTH passes (~2 min)

### 2.1 The CLI rebase command runs symlink-rebase AND dazzlelink-rebase
- [ ] In a dir holding BOTH a real symlink `[needs privilege]` and a stale `.dazzlelink`, run `rebase`.
  Expected: the symlink pass and the "Rebasing N dazzlelink file(s)..." pass both run; both kinds get
  fixed. If unprivileged, at least confirm the `.dazzlelink` pass runs (the "Rebasing ..." line appears).

## Section 3: Monolith parity (~3 min)
- [ ] Run the same rebase + `execute --mode info` against `python legacy/dazzlelink_monolith.py ...` and
  confirm equivalent results (same changed/unchanged counts, same info fields).
