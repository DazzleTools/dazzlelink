# Human Test Checklist: Executable Generation + Execute Mode Precedence (parity Commit 1)

**Target version:** 0.7.2
**Ships with commit:** TBD — "fix: executable generation + execute mode precedence (#18, #19)"
**Companion automated tests:** 10 — `tests/test_executable_and_mode_precedence.py` (5: executable no-raise, json-import smoke, file-beats-global, CLI-beats-file, fieldless→info), `tests/test_version.py` (5)

## What this is

This checklist verifies the first parity commit of the monolith→modular reassessment. The automated
tests prove the code paths no longer crash and that the precedence *resolves* correctly — but they mock
the actual `os.startfile`/`xdg-open` launch and they do not run the **generated executable script**.
This document covers what only a human at a real terminal can confirm: that a `convert --executable`
script actually *runs* under Windows `cmd.exe`/PowerShell (codepage 437/1252, no Unicode parse hazards),
that `execute` opens vs previews the right way for file-embedded vs global-config modes, and that the
flags (`--executable`, `--mode`) really land in the produced files.

A full pass is ~15 minutes; the High-Value section is ~5.

## Prerequisites

1. Windows 10/11 (primary) or Linux/macOS, Python ≥ 3.10, dazzlelink installed editable
   (`pip install -e .` from the repo root) so `python -m dazzlelink` runs the in-repo `src/` package.
2. **State isolation — non-negotiable:**
   - ALL operations happen inside a `%TEMP%`/`/tmp` sandbox. Never run `convert`/`execute`/`mirror`
     against a real project directory or real symlinks.
   - **DO NOT run** `scripts/dazzlelink_file_association_in_administrative_shell.{bat,ps1}` — registry writers.
   - The `open`/`auto` execute tests will actually launch the target in your default handler. Use a
     `.txt` target so it opens harmlessly in Notepad/your editor; close it after.
3. **Symlink note (Windows):** `convert` needs a real symlink to operate on. Creating one needs Developer
   Mode or an elevated shell. Steps that need it are flagged `[needs symlink privilege]`. If you lack it,
   mark them SKIP(privilege) and judge the error-message quality instead.

**Create the sandbox:**

**cmd.exe:**
```cmd
set DLT=%TEMP%\dl-c1
if exist "%DLT%" rmdir /s /q "%DLT%"
mkdir "%DLT%"
echo hello> "%DLT%\target.txt"
```

**PowerShell:**
```powershell
$env:DLT = "$env:TEMP\dl-c1"
if (Test-Path $env:DLT) { Remove-Item -Recurse -Force $env:DLT }
New-Item -ItemType Directory -Force $env:DLT | Out-Null
"hello" | Set-Content "$env:DLT\target.txt"
```

**POSIX:**
```bash
export DLT=/tmp/dl-c1
rm -rf "$DLT"; mkdir -p "$DLT"
echo hello > "$DLT/target.txt"
```

**Reset between sections:** delete and recreate the sandbox with the commands above.

## High-Value Verification (~5 minutes)

### HV.1 — `convert --executable` no longer crashes and produces a runnable script `[needs symlink privilege]`

Validates: #18 (the AttributeError) **and** the masked `json`-import crash in the generator.

- [ ] **Steps** (PowerShell; make a symlink, then convert with executable):
  ```powershell
  New-Item -ItemType SymbolicLink -Path "$env:DLT\link.txt" -Target "$env:DLT\target.txt" | Out-Null
  python -m dazzlelink convert "$env:DLT" --executable --mode open
  Get-ChildItem "$env:DLT\*.dazzlelink"
  ```
- [ ] **Expected:** exit 0, prints "Converted 1 symlinks…", and `link.txt.dazzlelink` exists. NO
  `AttributeError`, NO `name 'json' is not defined`.
- [ ] **Why this matters:** before this commit, `convert --executable` over any real symlink crashed —
  this is the headline bug the whole parity effort starts from.

### HV.2 — The generated executable script ACTUALLY RUNS (Windows codepage)

Validates: the produced script parses and runs under the real shell — mocks never execute it.

- [ ] **Steps:**

  **cmd.exe** (the generated `.dazzlelink` is a runnable script):
  ```cmd
  python "%DLT%\link.txt.dazzlelink" --info
  ```
  **PowerShell:**
  ```powershell
  python "$env:DLT\link.txt.dazzlelink" --info
  ```
- [ ] **Expected:** the script runs without a `SyntaxError`/`The string is missing the terminator` and
  prints target info. Inspect the file for Unicode hazards (see 2.3) — there should be none.
- [ ] **Why this matters:** a generated script with an em-dash/smart-quote would pass every Python test
  but die in `cmd.exe` codepage 437 — exactly the class of bug mocks can't see.

### HV.3 — `execute --mode info` previews (does not open)

Validates: info mode and the display.

- [ ] **Steps** (cross-shell):
  ```
  python -m dazzlelink create "<SANDBOX>/target.txt" "<SANDBOX>/info.dazzlelink"
  python -m dazzlelink execute --mode info "<SANDBOX>/info.dazzlelink"
  ```
- [ ] **Expected:** prints "DazzleLink Information:" with Target line; **nothing opens**. Exit 0.
- [ ] **Why this matters:** info is the safe default; it must never launch anything.

### HV.4 — File-embedded `open` mode wins over the global default (#19 fix)

Validates: the precedence decision (file beats global).

- [ ] **Steps** (create a file whose embedded mode is `open`, then execute with no `--mode`):
  ```
  python -m dazzlelink create "<SANDBOX>/target.txt" "<SANDBOX>/open.dazzlelink" --mode open
  python -m dazzlelink execute "<SANDBOX>/open.dazzlelink"
  ```
- [ ] **Expected:** the target **opens** in your default `.txt` handler (Notepad/editor) — the file's
  `open` mode is honored, not overridden to `info`. Close the opened file afterward.
- [ ] **Why this matters:** this is the entire point of #19 — before the fix the global `info` default
  silently overrode the file's `open`.

### HV.5 — CLI `--mode` overrides the file's embedded mode

Validates: CLI is top of precedence.

- [ ] **Steps:**
  ```
  python -m dazzlelink execute --mode info "<SANDBOX>/open.dazzlelink"
  ```
- [ ] **Expected:** prints info; does **not** open, even though the file is embedded `open`.
- [ ] **Why this matters:** the user's explicit one-off `--mode` must always win.

### HV.6 — `update-config` runs (previously crashed on missing `import json`)

Validates: the second masked import bug.

- [ ] **Steps:**
  ```
  python -m dazzlelink update-config --help
  ```
  (If `update-config` is not yet a CLI subcommand in this build, instead run the smoke import:)
  ```
  python -c "from dazzlelink.operations.batch import update_config_batch; print('import ok')"
  ```
- [ ] **Expected:** no `NameError: name 'json' is not defined`. Help text or "import ok".
- [ ] **Why this matters:** `batch.py` used `json` six times without importing it — any path through
  `update_config_batch` would `NameError`.

## Section 1: Flag forwarding (convert/mirror) — was silently dropped (~3 min)

### 1.1 `--executable` and `--mode` land in the produced file `[needs symlink privilege]`

- [ ] **Steps** (after HV.1 produced `link.txt.dazzlelink` with `--executable --mode open`):

  **cmd.exe:** `findstr "default_mode" "%DLT%\link.txt.dazzlelink"`
  **PowerShell:** `Select-String -Pattern '"default_mode"' "$env:DLT\link.txt.dazzlelink"`
  **POSIX:** `grep default_mode "$DLT/link.txt.dazzlelink"`
- [ ] **Expected:** the embedded `default_mode` is `"open"` (the `--mode` flag was forwarded), and the
  file is a script wrapper not bare JSON (the `--executable` flag was forwarded).
- [ ] **Check:** repeat without `--executable` → the file should be plain JSON (the `store_true` flag
  defaults False, matching the monolith).

### 1.2 `convert` without `--executable` produces plain JSON `[needs symlink privilege]`

- [ ] **Steps:** reset sandbox, remake the symlink, `python -m dazzlelink convert "<SANDBOX>"`.
- [ ] **Expected:** `link.txt.dazzlelink` is valid JSON (`python -m json.tool` parses it), no script
  wrapper. Confirms the executable default is off unless asked (monolith parity).

## Section 2: Execute behaviors and the generated script (~5 min)

### 2.1 `open` vs `auto` mode

- [ ] **Steps:** `python -m dazzlelink execute --mode auto "<SANDBOX>/open.dazzlelink"`
- [ ] **Expected:** behaves like `open` (launches the target). Exit 0.

### 2.2 Missing-target error quality

- [ ] **Steps:** create an `open` dazzlelink, delete the target, then execute:
  ```
  python -m dazzlelink create "<SANDBOX>/target.txt" "<SANDBOX>/broken.dazzlelink" --mode open
  ```
  then delete `target.txt` (cmd `del`, PS `Remove-Item`, POSIX `rm`) and
  `python -m dazzlelink execute "<SANDBOX>/broken.dazzlelink"`
- [ ] **Expected:** a clear error listing what was tried (Absolute / Relative / Representations), not a
  raw traceback. Judge the message's readability.

### 2.3 Generated script has NO Unicode hazards (codepage safety)

- [ ] **Steps** (inspect the executable file from HV.1 for non-ASCII bytes):

  **PowerShell:**
  ```powershell
  $b = [IO.File]::ReadAllBytes("$env:DLT\link.txt.dazzlelink")
  ($b | Where-Object { $_ -gt 127 }).Count
  ```
  **POSIX:**
  ```bash
  grep -nP '[^\x00-\x7F]' "$DLT/link.txt.dazzlelink" || echo "ASCII-clean"
  ```
- [ ] **Expected:** zero non-ASCII bytes in the generated script (no em-dashes, smart quotes, arrows,
  checkmarks). The JSON payload may legitimately contain non-ASCII if the *path* did; for an ASCII
  sandbox path, expect 0.

## Section 2b: Execute an EXECUTABLE dazzlelink — fork-bomb safety (~2 min)

**Why this section exists:** the v1 checklist run did not cover executing a
*script-format* (`--executable`) dazzlelink via the real shell path. Doing so
previously caused a fork bomb — `execute` shelled out to run the `.dazzlelink`,
which re-triggered the `.dazzlelink` file association (`dazzlelink execute`),
recursing without bound. Fixed: `execute` now reads the embedded JSON and acts
on the target directly. These steps confirm it.

### 2b.1 Execute an executable dazzlelink with `--mode info` — must return, must NOT spawn

- [ ] **Steps** (PowerShell; create an executable dazzlelink, then execute it):
  ```powershell
  python -m dazzlelink create "$env:DLT\target.txt" "$env:DLT\exec.dazzlelink" --executable --mode open
  $before = (Get-Process python,pythonw -EA SilentlyContinue).Count
  python -m dazzlelink execute "$env:DLT\exec.dazzlelink" --mode info
  Start-Sleep -Milliseconds 500
  $after = (Get-Process python,pythonw -EA SilentlyContinue).Count
  "before=$before after=$after"
  ```
- [ ] **Expected:** prints "DazzleLink Information:" and returns in well under a second;
  `after` is not climbing (no runaway `pythonw.exe`). It must NOT hang or spawn windows.
- [ ] **Why this matters:** this is the exact path that fork-bombed. If process count
  climbs or the command hangs, STOP and do not ship.

### 2b.2 (Optional, launches one window) Execute an executable dazzlelink in open mode

- [ ] **Steps:** `python -m dazzlelink execute "$env:DLT\exec.dazzlelink"` — opens the
  TARGET (`target.txt`) **once** in your default handler. It must open the target, not
  re-run the dazzlelink. Close the window after. If a window storm starts, the fix
  regressed — kill `pythonw.exe`/`python.exe` immediately.

## Section 3: Precedence matrix (the #19 contract) (~3 min)

Confirm by eye the resolution table the automated tests assert (file beats global, monolith parity):

| CLI `--mode` | File embedded | Global config | Expected result |
|---|---|---|---|
| (none) | `open` | `info` (default) | **open** (HV.4) — file beats global |
| `info` | `open` | — | **info** (HV.5) — CLI beats file |
| (none) | `info` | — | **info** (HV.3) |
| (none) | *absent* | `open` (set) | **info** — fieldless file resolves to info; global is vestigial (monolith parity) |

- [ ] The first three are covered by HV.3/4/5. The fourth requires a file with no `default_mode` field
  and a global `~/.dazzlelinkrc.json` set to `open` — **skip unless you can isolate your real
  `~/.dazzlelinkrc.json`** (back it up first; see Cleanup). The automated test
  `test_fieldless_file_resolves_to_info_not_global` already covers this without touching real dotfiles.
